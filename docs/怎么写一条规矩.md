# 怎么写一条规矩

写给想加规则或改规则的人。不要求会写代码，但要求**先有事故**。

## 第零步：先问「这条规矩命中的时候，谁错了」

如果答不上来，这条规矩不该写。

三种错法，对应三种动作：

| 错法 | 例子 | 动作 |
|---|---|---|
| **客观上就是错的** | 必填参数没给；往文件写中文却不带编码，读回来一定乱码 | `block` |
| **可疑但可能正当** | 命令里有写动词又带绝对路径——也可能就是要覆盖 | `steer` 或 `warn` |
| **只是不符合某人的习惯** | 搜东西时没指定用哪个引擎 | `default`，且只补空缺 |

只有第一种可以 `block`。把第三种写成 `block`，等于替用户做决定——用户会立刻把整个包卸掉。

## 第一步：从一次真实调用抄原始参数

规矩要判的是 `args`，所以得先有一条真实的 `args`。格式照抄，一字不差：

```json
{
  "tool": "pwsh",
  "args": {
    "description": "写配置文件",
    "command": "Set-Content -Path D:\\a\\b.txt -Value '中文'"
  }
}
```

**不要手写简化版**。手上这条真命令里有几个引号、有没有 here-string、`-Encoding` 在引号里还是外，直接决定规矩判得对不对。本仓库就踩过：一条 2961 字符的 here-string 命令，因为引号数量是奇数，旧实现的抹引号逻辑直接放弃处理，结果漏拦了一次。

## 第二步：把「错在哪」翻译成条件类型

十八种条件，多数场景只用得到四五种：

| 你想说的 | 用哪个 |
|---|---|
| 少了必填参数 | `missingKey` |
| 给了但是空的 | `emptyValue` |
| 这组参数至少要有一个 | `missingAnyOf` |
| 键名写错了（形近） | `wrongKey` |
| 多给了不该给的键 | `extraKey` |
| 值是字符串但应该是数字 | `typeMismatch` |
| 命令行里少了某个开关 | `missingFlag` |
| 出现了不该出现的词 | `regexHit` |
| **不该消失的词消失了** | `regexMiss` |
| 文件没有 BOM | `fileLacksBom` |
| 文件有 BOM（反过来） | `fileHasBom` |
| 找不到要替换的原文 | `fileAnchorMissing` |
| 要替换的原文出现多次 | `fileAnchorMultiple` |
| 文件比某个时间新 | `fileNewerThan` |
| 文件比程序启动还新（说明改完没重启） | `fileNewerThanProcessStart` |
| 写了契约里没有的键 | `unknownKey` |
| 路径跑出了允许范围 | `pathOutside` |
| 命令往绝对路径写文件 | `cmdAbsPathWritten` |

想组合就套 `all` / `any` / `not`。要表达「命令里没有 -Encoding」，正确写法是：

```json
{ "any": [
    { "type": "missingFlag", "flag": "-Encoding" },
    { "type": "regexMiss",  "in": "args.command", "pattern": "-Encoding" }
] }
```

或者直接用取反：

```json
{ "not": { "type": "regexHit", "in": "args.command", "pattern": "-Encoding" } }
```

## 第三步：把范围写紧（最容易漏的一步）

`appliesTo` 决定这条规矩管到多宽。**漏写等于管全部。**

本仓库真实踩过的坑：三条本该只管 `.ps1` 的规矩，`appliesTo` 里只写了工具名，结果会拦下「往 .txt 写中文」这种完全正常的操作。

```json
"appliesTo": {
  "tool": "pwsh",
  "commandMatches": "Set-Content|Add-Content|Out-File",
  "fileMatches": "\\.ps1$",        ← 少了这一行，你就是拦了所有文件
  "platform": ["win32"],
  "shell": ["powershell-5.1"]
}
```

**写完一定验一遍**：写个脚本，拿两个路径分别跑你的 `fileMatches`，一个该命中、一个该不命中。

```js
new RegExp("\\\\.ps1$").test("a.ps1")  // 必须 true
new RegExp("\\\\.ps1$").test("a.txt")  // 必须 false
```

正则里的反斜杠只有两个，不要写四个。在 JSON 里 `"\\.ps1$"` 表示正则的 `\.ps1$`。

## 第四步：写自测用例（这条最省事，也最容易跳过）

```json
"selfTest": {
  "cases": [
    { "args": { "command": "Set-Content -Path a.txt -Value 'x'" }, "expect": "block" },
    { "args": { "command": "Set-Content -Path a.txt -Value 'x' -Encoding UTF8" }, "expect": "pass" }
  ]
}
```

**只有「该拦」的用例是不够的。** 一条规矩如果宽到把所有东西都拦，它在只有「该拦」用例的情况下会完美通过。

依赖真实文件的（判 BOM、判锚点在不在、判文件新旧），标 `"needFs": true` 并把 `cases` 留空。**不要编一个假的用例假装跑过**——那比不写更糟。

## 第五步：写清 evidence

```json
"evidence": {
  "hits": 29,
  "sessions": 16,
  "source": "作者环境实测（次数与时间不公开）"
}
```

自己的包写多细都行；**进 `catalog/` 判据库的条目一律只写抽象案例**：不写会话号、不写具体时间戳、不写本机路径与真名，`source` 统一写「作者环境真实命中过（次数、时间、会话号不公开）」。详细日志留在作者本机，公开的只是结论。

没有 evidence 的规矩不会被拒装，但体检报告会把它列进「从没命中过」。

这句话有两面：可能是**多余的**（该删了），也可能只是**还没遇到**。体检报告只负责指出来，删不删由你判断。

## 第五步之二：要进判据库，就写四行

规矩在包里长什么样由 `rules.json` 决定；**进 `catalog/` 的每一条只有一种写法——四行**，`tools/validate.js` 会逐条卡，缺一行直接拒：

```json
"notes": [
  "判据：这条检查的是什么（一句话，不写正则，正则留在 rules.json 里）",
  "例子｜该拦：`真实的命令`；不该拦：`几乎一样但不该拦的`",
  "边界：哪些情况放过（这条最容易漏，也最决定别人会不会被它烦）",
  "场景例：这条为什么存在，一句话写那次事故"
]
```

四条要求：`判据：` 和 `边界：` 缺一个字都进不了库；例子必须正反两个都有，只有「该拦」的组合会被拦下——一条宽到什么都拦的规矩，在只有该拦用例时是满分。

依赖真实文件的条目（`needFs: true`）写不出可跑的例子，就写「例子：说明型条目，判定在 rules.json 里」，`边界：` 照写。

## 第六步：装前跑一遍

**在本仓库能跑的是结构校验**：

```bash
node tools/validate.js packs/windows-powershell
```

**装了完整版软件之后**，还能让引擎逐条跑你的用例（只装你这一条，避免别的规矩把它拦了导致误判）：

```js
const packmgr = require('<安装目录>/engine/packmgr');
const r = packmgr.selftestPack('packs/windows-powershell');
// { rules: 8, casesRan: 26, failedRules: [], needFs: 1, untested: 0, ok: true }
```

一条不过就不装。失败原因会说人话，例如「该拦的例子没拦住」或「条件抛错（不是命中，是没判成）」。

## 常见的四个错误

1. **把 `regexMiss` 当 `not regexHit` 用**。语义一样，但缺字段时不同：`regexMiss` 在字段不存在时返回 false（没给 ≠ 值不对），`not regexHit` 会返回 true。
2. **在 `pattern` 里写中文引号**。日志里的引号可能是弯引号也可能是直角引号，正则匹配不到。要么用 `[“”「」]` 这类字符组，要么先规范化。
3. **一个规矩包揽三件事**。拆开。规矩的 `title` 如果要用「并且」才能说清，说明它该拆成两条。
4. **改了规矩忘了改用例**。改了判定条件但用例没动，自测会「通过」——因为用例测的是旧行为。改条件时先改用例，让它先红再绿。

## 最后一条

如果一条规矩上线后从来没命中过，而你又确认场景确实会经过它——**先怀疑它写错了**，别怀疑「还没遇到」。
本仓库有条规矩，就是靠「8 条里只有 5 条有证据」这个体检结果，才发现三条里的 `fileMatches` 漏了。
